## 1. 通用规范

### 1.1 JSON命名规范

**强制要求**：所有JSON字段必须使用下划线命名法（snake_case）

| 场景 | 示例 |
|------|------|
| Diff接口入参 | migration_key, new_json, old_json |
| Diff接口响应 | has_diff, diff_results |
| 迁移任务API | migration_key, target_status, create_time, update_time |
| 灰度规则配置 | migration_key, rule_type, rule_value, enable |
| Diff规则配置 | migration_key, rule_type, field_path, rule_value, enable |
| 配置中心存储 | 所有配置均使用下划线命名法 |

**错误示例**（禁止使用）：
```json
{
    "migrationKey": "xxx",
    "hasDiff": true,
    "ruleType": "IGNORE",
    "newJson": "xxx"
}
```

**正确示例**：
```json
{
    "migration_key": "xxx",
    "has_diff": true,
    "rule_type": "IGNORE",
    "new_json": "xxx"
}
```

### 1.2 枚举值规范

**强制要求**：在使用 Java 或前端 TypeScript 等语言体系下，所有枚举值必须使用大写下划线命名法（UPPER_SNAKE_CASE）。在使用 Go 语言开发 SDK 或后端服务时，枚举值和常量名**必须遵循 Go 语言的帕斯卡命名法（PascalCase/大驼峰）**。

| 场景 | Java/前端 正确规范 | Go 语言正确规范 |
|------|------|------|
| 灰度规则类型 | PERCENTAGE, BLACKLIST, WHITELIST, EXPRESSION | Percentage, Blacklist, Whitelist, Expression |
| Diff规则类型 | IGNORE, TOLERANCE, SCRIPT, SORT | Ignore, Tolerance, Script, Sort |
| 迁移状态 | OLD, VALIDATION_GRAY, VALIDATION_ALL | Old, ValidationGray, ValidationAll |

### 1.3 服务与模块命名规范

**强制要求**：微服务及工程模块的命名需要清晰区分模块名与服务注册名（即 `spring.application.name` 或等效配置），必须遵守以下对应关系：

| 模块用途 | 模块/目录名 (Module Name) | 服务名称 (Service Name) |
|------|------|------|
| 管理后台 API | migration-admin-api | migration.admin.api |
| 管理后台 UI | migration-admin-ui | migration.admin.ui |
| Diff 对比服务 | migration-diff-service | migration.diff.service |

- **模块名/目录名**（如 Maven Artifact ID 或前端根目录名）：使用中线连接命名法（kebab-case）。
- **服务名称**（配置中心、注册中心、Docker 容器名等）：使用点分隔命名法（dot notation）。

## 2. Java开发规范

### 2.1 代码风格

- 遵循Google Java Style Guide
- 使用4空格缩进
- 行长度限制120字符
- 文件编码UTF-8
- 强制使用Lombok注解简化代码（@Data、@Builder、@AllArgsConstructor、@NoArgsConstructor等）

### 2.2 注释规范

**强制要求**：注释尽量多，能用中文尽量用中文写

- 类和方法必须添加Javadoc注释，说明功能、参数、返回值
- 关键逻辑必须添加行内注释说明
- TODO注释格式：// TODO: 说明

```java
/**
 * 迁移客户端，用于包装新旧接口方法
 * 根据当前迁移状态决定调用旧接口、新接口或并发调用
 */
public class MigrationClient {

    /**
     * 包装方法，将旧接口、新接口、降级方法包装成可执行的函数
     *
     * @param oldMethod 旧接口方法引用
     * @param newMethod 新接口方法引用
     * @param fallbackMethod 降级方法（可选，为null时默认降级走旧接口）
     * @param paramHandler 参数打包器，用于构建灰度匹配参数
     * @return 执行函数
     */
    public <T> ExecuteFunction<T> wrap(
            Function<Object[], T> oldMethod,
            Function<Object[], T> newMethod,
            BiFunction<Object[], Exception, T> fallbackMethod,
            ParamHandler paramHandler) {
        // 根据当前迁移状态决定调用逻辑
        // ...
    }
}
```

### 2.3 命名规范

| 类型 | 规范 | 示例 |
| 类名 | 大驼峰 | MigrationClient, DiffService |
| 方法名 | 小驼峰 | execute, wrap, buildParam |
| 变量名 | 小驼峰 | config, migrationKey, paramHandler |
| 常量 | 全大写下划线 | DEFAULT_POOL_SIZE, MAX_RETRY_COUNT |
| 包名 | 全小写 | com.migration.sdk, com.migration.starter |

### 2.4 枚举规范

**强制要求**：对于可枚举的值，尽量使用枚举类定义

```java
/**
 * 迁移状态枚举
 * 1-单旧(Old)：只调用旧接口
 * 2-验证-灰度(Validation-gray)：并发调用，进行Diff，返回旧接口结果
 * 3-验证-全开(Validation-all)：并发调用，进行Diff，返回旧接口结果
 * 4-上线-灰度(Go-Live-gray)：并发调用，进行Diff，根据灰度规则返回
 * 5-上线-全开(Go-Live-all)：并发调用，进行Diff，返回新接口结果
 * 6-停用-灰度(Decommissioning-gray)：根据灰度规则调用新接口或并发调用
 * 7-停用-全开(Decommissioning-all)：只调用新接口
 */
@Getter
@AllArgsConstructor
public enum MigrationTaskStatus {

    OLD(1, "单旧"),
    VALIDATION_GRAY(2, "验证-灰度"),
    VALIDATION_ALL(3, "验证-全开"),
    GO_LIVE_GRAY(4, "上线-灰度"),
    GO_LIVE_ALL(5, "上线-全开"),
    DECOMMISSIONING_GRAY(6, "停用-灰度"),
    DECOMMISSIONING_ALL(7, "停用-全开");

    private final int code;
    private final String desc;
}
```

### 2.5 接口定义

```java
// ParamHandler接口（SDK定义，供SDK和Starter共用）
@FunctionalInterface
public interface ParamHandler {
    /**
     * 将原接口参数转换为灰度匹配参数
     * @param args 原接口的方法参数
     * @return 灰度匹配参数Map
```

### 2.6 注解规范

```java
// Spring Boot Starter @Migration注解
@Target(ElementType.METHOD)
@Retention(RetentionPolicy.RUNTIME)
public @interface Migration {
    String key();
    String oldMethod();
    String newMethod();
    String fallBackMethod() default "";
    Class<? extends ParamHandler> paramHandler() default ParamHandler.class;
    int corePoolSize() default 2;
    int maxPoolSize() default 10;
    int queueCapacity() default 100;
    String threadNamePrefix() default "migration-";
}
```

### 2.7 日志规范

- 使用SLF4J日志框架
- 日志级别：ERROR用于异常，WARN用于警告，INFO用于关键流程，DEBUG用于调试
- 日志内容需包含关键上下文信息

```java
// 正确示例
log.info("Migration started, migrationKey={}, status={}", migrationKey, status);
log.error("Diff failed, migrationKey={}, error={}", migrationKey, e.getMessage(), e);

// 错误示例
log.info("开始迁移");
log.error("错误");
```

## 3. Go开发规范

### 3.1 代码风格

- 遵循Go官方编码规范
- 使用gofmt格式化代码
- 行长度限制100字符（IDE可配置）

### 3.2 注释规范

**强制要求**：注释尽量多，能用中文尽量用中文写

- 函数和方法必须添加注释，说明功能、参数、返回值
- 关键逻辑必须添加行内注释说明

```go
// 全局通用配置（不包含MigrationKey，MigrationKey在Wrap时传入）
type Config struct {
    AdminUrl       string
    DiffServiceUrl string
}

// NewClient 创建迁移客户端
// 参数config: 迁移配置
// 返回值: 迁移客户端实例
```

## 4. Git管理规范

### 4.1 分支管理

| 分支 | 用途 | 命名规则 |
|------|------|---------|
| master | 主分支，生产环境代码 | - |
| develop | 开发分支 | - |
| feature/* | 功能开发 | feature/功能名称 |
| bugfix/* | Bug修复 | bugfix/问题描述 |
| hotfix/* | 紧急修复 | hotfix/问题描述 |
| release/* | 发布准备 | release/版本号 |

### 4.2 提交规范

**提交信息格式**：
```
<type>(<scope>): <subject>

<body>

<footer>
```

**type类型**：
| 类型 | 说明 |
|------|------|
| feat | 新功能 |
| fix | Bug修复 |
| docs | 文档变更 |
| style | 代码格式（不影响功能）|
| refactor | 重构（既不是新功能也不是修复）|
| test | 测试相关 |
| chore | 构建过程或辅助工具变动 |

**scope范围**：
- sdk: SDK相关
- starter: Spring Boot Starter相关
- diff: Diff服务相关
- admin: 管理后台相关
- config: 配置中心相关

**示例**：
```
feat(sdk): add wrap method for Java SDK

Add wrap method that accepts method references and ParamHandler
to support flexible parameter handling for grayscale matching.

Closes #123
```

### 4.3 Commit Message检查

- 使用commit-hooks检查提交信息格式
- subject首字母小写
- subject不超过50字符
- body说明what和why，不说明how

## 5. API设计规范

### 5.1 API风格

**强制要求**：不使用RESTful风格，路径中体现方法类型，只使用GET和POST（尽量用POST）

**URL规范**：
- 路径使用小写下划线命名法
- 体现操作类型：/api/v1/migration_task/create、/api/v1/migration_task/update、/api/v1/migration_task/query

**示例**：
```
POST   /api/v1/migration_task/create     # 创建迁移任务
POST   /api/v1/migration_task/update     # 更新迁移任务
POST   /api/v1/migration_task/query     # 查询迁移任务
POST   /api/v1/migration_task/delete    # 删除迁移任务
POST   /api/v1/grayscale_rule/create    # 创建灰度规则
POST   /api/v1/diff_rule/create         # 创建Diff规则
POST   /api/v1/diff                     # 执行Diff比对
GET    /api/v1/migration_task/list       # 获取任务列表
```

### 5.2 响应格式

```json
{
    "code": 0,
    "message": "success",
    "data": {}
}
```

| 字段 | 类型 | 说明 |
|------|------|------|
| code | Integer | 0成功，非0失败 |
| message | String | 提示信息 |
| data | Object | 响应数据 |

### 5.2.1 分页响应格式

**强制要求**：List接口必须使用PageResult进行分页返回

```json
{
    "code": 200,
    "message": "success",
    "data": {
        "current": 1,
        "size": 10,
        "total": 100,
        "list": []
    }
}
```

说明：`totalPages`、`hasNext` 在 `common-base` 的 `PageResult` 中使用 `@JsonIgnore`，不参与JSON输出。

**Java使用示例**：
```java
// 分页查询
PageResult<User> result = PageResult.of(current, size, total, userList);
return Result.success(result);
```

**Go使用示例**：
```go
// 分页响应
result := NewPageResult(userList, total, page, pageSize)
return Result{Code: 0, Data: result}
```

### 5.3 错误码规范

| 1000-1999 | 通用错误 |
| 2000-2999 | SDK错误 |

| 4000-4999 | 管理后台错误 |

## 10. 发布规范

### 10.1 版本号规范

遵循语义化版本号：MAJOR.MINOR.PATCH

| 级别 | 说明 | 示例 |
|------|------|------|
| MAJOR | 不兼容的API变更 | 1.0.0 -> 2.0.0 |
| MINOR | 向后兼容的功能新增 | 1.0.0 -> 1.1.0 |
| PATCH | 向后兼容的问题修复 | 1.0.0 -> 1.0.1 |

### 10.2 发布流程

1. 从develop分支创建release分支
2. 更新版本号
3. 执行测试和构建
4. 合并到master分支并打标签
5. 合并回develop分支
