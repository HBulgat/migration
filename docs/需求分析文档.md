## 1. 项目背景

### 1.1 问题陈述

在微服务架构或遗留系统升级场景方经常需要将中，业务底层接口从旧版本迁移到新版本。直接切换风险极高，一旦新接口出现问题，将直接影响线上业务，造成不可逆的事故。

### 1.2 目标

提供一个渐进式的接口迁移平台，通过以下机制保证迁移的稳定性：
1. **灰度验证**: 允许小比例流量先尝试新接口
2. **并行调用**: 新旧接口同时运行，进行结果对比
3. **平滑切换**: 支持7个渐进阶段，降低单次切换风险
4. **可回滚**: 支持任意阶段回滚到初始状态

### 1.3 项目范围

本平台是一个完整的接口迁移解决方案，包含：
- 迁移任务管理后台（前后端 + API）
- Diff对比服务（独立微服务）
- 多语言SDK（Java、Go）

## 2. 术语定义

| 术语 | 定义 |
|------|------|
| 迁移任务 | 一次完整的接口迁移过程，从旧接口迁移到新接口 |
| 接口 | 一个方法，可以是HTTP接口、RPC接口、Java方法或Go函数 |
| 旧接口(Old API) | 被迁移的原有接口（可以是HTTP、RPC、Java方法、Go函数） |
| 新接口(New API) | 目标接口，即迁移后的新版本接口 |
| 灰度规则 | 用于决定请求是否走新接口的规则条件 |
| Diff | 新旧接口返回值的对比分析 |
| 业务方 | 使用本平台进行接口迁移的开发团队 |
| migrationKey | 迁移任务的唯一标识键，用于在配置中心中定位配置 |
| Param | 业务接入方主动打包的灰度匹配参数，包含用于匹配灰度规则的数据 |

## 3. 系统架构概述

### 3.1 逻辑架构

```
┌─────────────────────────────────────────────────────────────────┐
│                         业务方接入层                              │
│  ┌─────────────┐                    ┌─────────────┐            │
│  │  Java SDK   │                    │   Go SDK    │            │
│  └─────────────┘                    └─────────────┘            │
└─────────────────────────────────────────────────────────────────┘
          │                                    │
          │ 拉取配置                           │ 发送Diff请求
          ▼                                    ▼
┌─────────────────────────────────────────────────────────────────┐
│                      迁移任务管理后台                             │
│  ┌─────────────┐  ┌─────────────┐  ┌─────────────┐            │
│  │  Web前端    │  │  后端API    │  │   配置中心   │            │
│  └─────────────┘  └─────────────┘  └─────────────┘            │
└─────────────────────────────────────────────────────────────────┘
          │
          │ 拉取配置
          ▼
┌─────────────────────────────────────────────────────────────────┐
│                        Diff 服务                                 │
│              (独立微服务，支持横向扩展)                           │
└─────────────────────────────────────────────────────────────────┘
```

**SDK与Diff服务通信说明**：
- SDK在需要进行Diff时，将新旧接口的返回值发送给Diff服务
- Diff服务根据migrationKey查询对应的Diff规则进行比对
- 返回比对结果（hasDiff和diffResults）

### 3.2 核心组件

| 组件 | 说明 | 职责 |
|------|------|------|
|------|------|------|
| Java SDK | 供Java业务方集成 | 封装迁移逻辑，处理接口调用 |
| Go SDK | 供Go业务方集成 | 封装迁移逻辑，处理接口调用 |
| 管理后台API | 迁移任务管理 | 提供任务创建、状态切换、规则配置等API |
| Web前端 | 管理界面 | 任务管理、配置管理、监控展示 |
| 配置中心 | 规则管理 | 存储灰度规则、Diff配置 |
| Diff服务 | 比对服务 | 新旧接口返回值对比，支持自定义脚本 |

## 4. 功能需求

### 4.1 迁移任务管理

#### 4.1.1 任务创建

**需求描述**: 业务方可以创建一个新的迁移任务

**输入参数**:

| 参数名 | 类型 | 必填 | 说明 |
|--------|------|------|------|
| migration_key | String | 是 | 迁移任务唯一标识键 |
| description | String | 否 | 任务描述 |

**业务规则**:
- migration_key在系统中必须唯一
- 配置中心中以migration_key作为主键存储所有配置

#### 4.1.2 任务状态查询

**需求描述**: 查询迁移任务的当前状态

**输出参数**:

| 参数名 | 类型 | 说明 |
|--------|------|------|
| migration_key | String | 迁移任务唯一标识键 |
| status | Integer | 当前状态(1-7) |
| create_time | DateTime | 创建时间 |
| update_time | DateTime | 更新时间 |

#### 4.1.3 任务状态切换

**需求描述**: 修改迁移任务的当前阶段

**输入参数**:

| 参数名 | 类型 | 必填 | 说明 |
|--------|------|------|------|
| migration_key | String | 是 | 迁移任务唯一标识键 |
| target_status | Integer | 是 | 目标状态(1-7) |

**业务规则**:
- 向前切换（升级）: 必须按顺序，即第N阶段 → 第N+1阶段
- 向后切换（降级）: 任意跳转，例如第7阶段 → 第1阶段

### 4.2 迁移阶段定义

本系统定义了7个迁移阶段，每个阶段对应不同的调用逻辑：

| 阶段 | 状态码 | 旧接口 | 新接口 | 返回值来源 | Diff | 灰度规则 |
|------|--------|--------|--------|------------|------|---------|
| 单旧(Old) | 1 | ✓ | ✗ | 旧接口 | ✗ | ✗ |
| 验证-灰度(Validation-gray) | 2 | ✓ | ✓(并发) | 旧接口 | ✓ | ✓ |
| 验证-全开(Validation-all) | 3 | ✓ | ✓(并发) | 旧接口 | ✓ | ✗ |
| 上线-灰度(Go-Live-gray) | 4 | ✓ | ✓(并发) | 命中→新,未命中→旧 | ✓ | ✓ |
| 上线-全开(Go-Live-all) | 5 | ✓ | ✓(并发) | 新接口 | ✓ | ✗ |
| 停用-灰度(Decommissioning-gray) | 6 | 未命中→✗,命中→✓ | ✓ | 新接口 | ✓ | ✓ |
| 停用-全开(Decommissioning-all) | 7 | ✗ | ✓ | 新接口 | ✗ | ✗ |

#### 4.2.1 阶段详细说明

**阶段1: 单旧(Old)**
- 仅调用旧接口
- 返回旧接口的响应
- 不进行Diff

**阶段2: 验证-灰度(Validation-gray)**
- 并发调用新接口和旧接口
- 返回旧接口的响应
- 进行Diff对比
- 灰度规则：命中规则走新接口，未命中走旧接口（均进行Diff）

**阶段3: 验证-全开(Validation-all)**
- 并发调用新接口和旧接口
- 返回旧接口的响应
- 进行Diff对比
- 所有流量都进行Diff

**阶段4: 上线-灰度(Go-Live-gray)**
- 并发调用新接口和旧接口
- 进行Diff对比
- 灰度规则：命中规则返回新接口响应，未命中返回旧接口响应

**阶段5: 上线-全开(Go-Live-all)**
- 并发调用新接口和旧接口
- 进行Diff对比
- 返回新接口的响应

**阶段6: 停用-灰度(Decommissioning-gray)**
- 灰度规则命中：仅调用新接口，返回新接口响应
- 灰度规则未命中：调用新接口和旧接口，进行Diff，返回新接口响应

**阶段7: 停用-全开(Decommissioning-all)**
- 仅调用新接口
- 返回新接口的响应
- 不进行Diff

### 4.3 灰度规则管理

#### 4.3.1 规则创建

**需求描述**: 为迁移任务配置灰度规则，存储到配置中心

**输入参数**:

| 参数名 | 类型 | 必填 | 说明 |
|--------|------|------|------|
| migration_key | String | 是 | 迁移任务唯一标识键 |
| rule_type | Enum | 是 | 规则类型(PERCENTAGE/BLACKLIST/WHITELIST/EXPRESSION) |
| rule_value | String | 是 | 规则值 |
| enable | Boolean | 是 | 是否启用 |

**规则类型说明**:

| 类型 | 说明 | rule_value示例 |
|------|------|---------------|
| PERCENTAGE | 按百分比灰度 | "30" 表示30%流量走新接口 |
| BLACKLIST | 黑名单 | "[\"1001\",\"1002\",\"1003\"]" json数组字符串，表示这些ID不走新接口 |
| WHITELIST | 白名单 | "[\"1001\",\"1002\",\"1003\"]" json数组字符串，表示只有这些ID走新接口 |
| EXPRESSION | 表达式匹配 | 待技术选型后确定（可能是SpEL、Groovy等） |

#### 4.3.2 Param参数打包

**需求描述**: 业务接入方主动打包灰度匹配参数，供SDK进行灰度规则匹配

Param是一个Map结构，由业务方自行定义键值对，用于灰度规则匹配：

**使用示例**:
```java
// 业务方打包Param（Map结构）
Map<String, Object> param = new HashMap<>();
param.put("userId", "1001");
param.put("level", 5);
param.put("area", "beijing");
```

### 4.4 Diff配置管理

#### 4.4.1 Diff规则创建

**需求描述**: 配置Diff比对规则，存储到配置中心

**输入参数**:

| 参数名 | 类型 | 必填 | 说明 |
|--------|------|------|------|
| migration_key | String | 是 | 迁移任务唯一标识键 |
| rule_type | Enum | 是 | 规则类型(IGNORE/TOLERANCE/SCRIPT/SORT) |
| field_path | String | 是 | 字段路径(JSONPath格式，如：data.price) |
| rule_value | String | 否 | 规则值 |
| enable | Boolean | 是 | 是否启用 |

**规则类型说明**:

| 类型 | 说明 | rule_value |
|------|------|----------|
| IGNORE | 忽略比对 | 空 |
| TOLERANCE | 误差容忍 | 误差范围值（如0.01表示允许0.01的误差） |
| SCRIPT | 自定义脚本 | SpEL表达式内容（返回Boolean，true=上报差异，false=忽略） |
| SORT | 排序规则 | 数组元素排序字段（如id、orderId），比对前先排序 |

**自定义脚本变量（SpEL）**:
- `#oldValue`: 差异项旧值
- `#newValue`: 差异项新值
- `#fieldPath`: 差异字段路径
- `#diffType`: 差异类型（ADD/REMOVE/MODIFY）

**自定义脚本示例（SpEL）**:
```spel
#fieldPath == 'data.detail' and #oldValue != null and #newValue != null
```

#### 4.4.2 多规则配置

一个migrationKey可以配置多条Diff规则，形成规则链。Diff比对时会依次应用所有规则。

### 4.5 SDK功能需求

#### 4.5.1 Java SDK

**核心功能**:

| 功能 | 说明 |
|------|------|
| 集成简单 | 引入jar包，配置少量参数即可使用 |
| 配置获取扩展点 | 支持通过后端API拉取配置，后续可扩展为直接读配置中心 |
| 并发调用 | 新旧接口并发调用，不影响响应时间 |
| 结果对比 | 自动进行Diff并上报结果 |
| 自定义降级方法 | 允许业务方自定义降级逻辑，默认降级走旧接口 |

**Config结构**:
```java
public class MigrationConfig {
    private String migrationKey;
    // getter/setter
}
```

**核心类说明**:

| 类名 | 说明 |
|------|------|
| MigrationConfig | 迁移配置类，仅包含migrationKey |
| MigrationClient | 迁移客户端，用于包装方法 |
| ExecuteFunction | 执行函数接口 |
| ParamHandler | 参数打包接口，SDK定义，供SDK和Starter共用 |

**ParamHandler接口** (SDK定义，供SDK和Starter共用):
```java
@FunctionalInterface
public interface ParamHandler {
    /**
     * 将原接口参数转换为灰度匹配参数
     * @param args 原接口的方法参数
     * @return 灰度匹配参数Map
     */
    Map<String, Object> build(Object... args);
}
```

**使用示例**:
```java
// 1. 定义接口方法（无论几个参数都可以）
User getUserOld(String id, Integer level);
User getUserNew(String id, Integer level);
User getUserFallback(String id, Integer level, Exception e);

// 1. 创建ParamHandler对象
ParamHandler paramHandler = (Object... args) -> {
    String id = (String) args[0];
    Integer level = (Integer) args[1];
    Map<String, Object> param = new HashMap<>();
    param.put("userId", id);
    param.put("level", level);
    return param;
};

// 2. 创建Config
MigrationConfig config = new MigrationConfig();
config.setMigrationKey("user-getUser-api");

// 3. 创建Client
MigrationClient client = new MigrationClient(config);

// 4. 使用wrap方法包装新旧接口和降级方法
// 前三个参数使用方法引用，第4个参数是ParamHandler对象实例
ExecuteFunction<User> execute = client.wrap(
    this::getUserOld,      // 方法引用
    this::getUserNew,      // 方法引用
    this::getUserFallback, // 方法引用（可选，为空则默认降级走旧接口）
    userParamHandler       // ParamHandler对象实例
);

// 5. 执行（传入原接口的参数）
User user = execute.apply("1001", 5);
```

#### 4.5.2 Java SDK - Spring Boot Starter

在Java SDK基础上，提供Spring Boot Starter，方便Spring项目集成：

**功能**:
- 自动配置MigrationClient
- 通过注解方式定义迁移
- 支持与Spring生态无缝集成

**@Migration注解说明**:

| 属性 | 类型 | 必填 | 说明 |
|------|------|------|------|
| key | String | 是 | migration_key，迁移任务唯一标识 |
| oldMethod | String | 是 | 旧方法名称（同一类中的方法名） |
| newMethod | String | 是 | 新方法名称（同一类中的方法名） |
| fallBackMethod | String | 否 | 降级方法名称（默认降级走旧接口） |
| paramHandler | Class | 否 | 参数打包类，需实现ParamHandler接口 |
| corePoolSize | int | 否 | 从流程线程池核心线程数，默认2 |
| maxPoolSize | int | 否 | 从流程线程池最大线程数，默认10 |
| queueCapacity | int | 否 | 从流程线程池队列容量，默认100 |
| threadNamePrefix | String | 否 | 从流程线程名称前缀，默认"migration-" |

**ParamHandler接口**: SDK中已定义，Starter中直接引用

**使用示例**:
```java
// 1. 创建参数打包类（实现SDK中定义的ParamHandler接口）
@Component
public class UserParamHandler implements ParamHandler {
    @Override
    public Map<String, Object> build(Object... args) {
        String id = (String) args[0];
        Integer level = (Integer) args[1];
        Map<String, Object> param = new HashMap<>();
        param.put("userId", id);
        param.put("level", level);
        return param;
    }
}

// 2. 在启动类上启用迁移
@EnableMigration
@SpringBootApplication
public class Application {
    public static void main(String[] args) {
        SpringApplication.run(Application.class, args);
    }
}

// 3. 使用@Migration注解定义迁移
@RestController
public class UserController {

    // 旧接口方法
    public User getUserOld(String id, Integer level) {
        return oldUserService.getUserById(id);
    }

    // 新接口方法
    public User getUserNew(String id, Integer level) {
        return newUserService.getUserById(id);
    }

    // 降级方法（可选）
    public User getUserFallback(String id, Integer level, Exception e) {
        return oldUserService.getUserById(id);
    }

    // 通过注解标记迁移方法
    @Migration(
        key = "user-getUser-api",
        oldMethod = "getUserOld",
        newMethod = "getUserNew",
        fallBackMethod = "getUserFallback",
        paramHandler = UserParamHandler.class,
        corePoolSize = 2,
        maxPoolSize = 10,
        queueCapacity = 100
    )
    @GetMapping("/user/{id}")
    public User getUser(@PathVariable String id, @RequestParam Integer level) {
        // 此方法不会被执行，仅作为方法签名参考
        return null;
    }
}
```

**线程池说明**:
- 主流程：使用调用方的线程池执行（即Controller所在的线程）
- 从流程：使用注解配置的线程池执行（新接口调用、Diff等）

#### 4.5.3 Go SDK

**核心功能**: 同Java SDK

**Config结构**:
```go
type Config struct {
    MigrationKey string
}
```

**使用示例**:
```go
// 1. 创建Config
config := &migration.Config{
    MigrationKey: "user-getUser-api",
}

// 2. 使用Wrap方法包装新旧接口和降级方法
// Wrap接收的函数签名应该是 func(id string, level int) (result, error)
client := migration.NewClient(config)
execute := client.Wrap(
    func(id string, level int) (interface{}, error) { return oldService.GetUser(id, level) },  // 旧接口
    func(id string, level int) (interface{}, error) { return newService.GetUser(id, level) }, // 新接口
    func(id string, level int, err error) (interface{}, error) { return oldService.GetUser(id, level) }, // 降级方法（可选）
    func(id string, level int) map[string]interface{} { // ParamHandler：构建灰度参数
        return map[string]interface{}{
            "userId": id,
            "level":  level,
        }
    },
)

// 3. 执行（传入原接口的参数）
user, err := execute.Execute("1001", 5)
```

#### 4.5.4 SDK配置获取扩展点

SDK获取配置的方式需要留有扩展点：

| 获取方式 | 说明 |
|---------|------|
| API拉取（默认） | 通过后端API拉取迁移配置 |

### 4.6 Diff服务

#### 4.6.1 Diff比对接口

Diff服务根据migrationKey查询配置中心中对应的Diff规则，进行比对。

**请求**:
```
POST /api/v1/diff
Content-Type: application/json

{
    "migration_key": "user-getUser-api",
    "new_json": "{\"name\":\"test\",\"price\":100.5}",
    "old_json": "{\"name\":\"test\",\"price\":100.0}"
}
```

**字段说明**:

| 字段 | 类型 | 说明 |
|------|------|------|
| migration_key | String | 迁移任务唯一标识键 |
| new_json | String | 新接口返回值的JSON字符串 |
| old_json | String | 旧接口返回值的JSON字符串 |

**响应**:
```json
{
    "has_diff": true,
    "diff_results": [
        {
            "path": "data.price",
            "new_value": 100.5,
            "old_value": 100.0
        },
        {
            "path": "data.orders",
            "new_value": null,
            "old_value": []
        }
    ]
}
```

**响应字段说明**:

| 字段 | 类型 | 说明 |
|------|------|------|
| has_diff | Boolean | 是否有差异 |
| diff_results | Array | 差异列表 |
| diff_results[].path | String | 差异字段路径 |
| diff_results[].new_value | Object | 新接口返回值 |
| diff_results[].old_value | Object | 旧接口返回值 |

## 5. 非功能需求

### 5.1 性能需求

| 指标 | 要求 |
|------|------|
| 接口响应时间 | 新旧接口并发调用，不增加额外延迟 |
| Diff服务响应时间 | P99 < 100ms |
| 管理后台接口响应时间 | P99 < 200ms |

### 5.2 可用性需求

| 指标 | 要求 |
|------|------|
| 系统可用性 | 99.9% |
| Diff服务降级 | Diff服务不可用时，记录日志，不影响业务返回 |

### 5.3 扩展性需求

- Diff服务支持横向扩展
- SDK支持多语言扩展
- 支持集群部署

### 5.4 安全性需求

- 管理后台需登录认证
- API需鉴权

## 7. 业务流程图

### 7.1 迁移任务生命周期

```
创建任务 → 阶段1(单旧) → 阶段2(验证-灰度) → 阶段3(验证-全开)
                                        ↓
                     阶段7(停用-全开) ← 阶段6(停用-灰度) ← 阶段5(上线-全开) ← 阶段4(上线-灰度)
```

### 7.2 请求处理流程

```
请求进入
    │
    ▼
获取当前阶段
    │
    ├── 阶段1: 仅调用旧接口 → 返回
    │
    ├── 阶段2/3: 并发调用新旧接口 → Diff → 返回旧接口结果
    │
    ├── 阶段4/5: 并发调用新旧接口 → Diff → 根据规则返回
    │
    ├── 阶段6: 根据规则判断
    │        ├── 命中: 调用新接口 → 返回
    │        └── 未命中: 并发调用 → Diff → 返回新接口结果
    │
    └── 阶段7: 仅调用新接口 → 返回
```
