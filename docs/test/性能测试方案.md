# 后端接口迁移平台性能测试方案

## 1. 概述
本方案旨在评估后端接口迁移平台在不同负载下的表现，识别潜在性能瓶颈，确保系统能够在高并发生产环境中稳定运行。核心关注点在于接入 SDK 后对业务系统的性能损耗（Overhead）。

## 2. 测试目标
**核心目标**：精确量化接入方接入 SDK 后在不同迁移阶段下的延迟增加、吞吐量下降及其比例。

- **SDK 性能损耗率**：对比 `(SDK 封装后性能 - 原始性能) / 原始性能`。
- **全阶段覆盖**：详细评估 7 个迁移阶段下，由于 SDK AOP 拦截、策略判定、Disruptor 异步处理带来的额外开销。
- **极限承载与稳定性**：观测在高压力下，SDK 异步队列（Disruptor）是否会导致业务应用内存溢出或线程争用，验证 Backpressure 机制。

## 3. 测试场景设计

### 3.1 SDK 性能损耗深度测试
模拟真实业务逻辑（如：多表级联查询 + 复杂数据聚合），对比“纯业务代码执行”与“SDK 封装后执行”在各阶段的表现。

#### 7 阶段全量对比矩阵
| 阶段 | 核心行为 | 性能预期 vs 基准 (Base) | 关键测试点 |
| :--- | :--- | :--- | :--- |
| **1. OLD** | 仅 AOP 拦截 + 读配置 + 调用旧逻辑 | RT 增加 < 1ms | AOP 代理及配置读取开销 |
| **2. VALIDATION_GRAY** | 并发调用新旧 + 异步 Diff 上报 | RT 略增 + CPU 提升 | 并行执行及队列推入开销 |
| **3. VALIDATION_ALL** | 同上，但 100% 并发 | RT 略增 + SDK 队列高负载 | 异步处理器的吞吐限制 |
| **4. GO_LIVE_GRAY** | 灰度判定 + 根据结果决定调用 | RT 波动 (视命中情况) | 灰度规则匹配计算耗时 |
| **5. GO_LIVE_ALL** | 并发调用 + 返回新结果 | RT = max(Old, New) | 强一致性比对下的总延迟 |
| **6. DECOMMISSIONING_GRAY** | 命中直调新，未命中并发 | RT 分支表现 | 条件分支判定效率 |
| **7. DECOMMISSIONING_ALL** | AOP 拦截 + 仅调用新逻辑 | RT 增加 < 1ms | 最终卸载前的平滑度 |

#### 业务模拟 (Business Simulation)
- **Data Load**：执行 2~3 个 SQL 关联查询（Join），结果集在 1KB ~ 10KB。
- **Mock Logic**：在代码中加入 5ms~10ms 的延迟以模拟真实业务处理耗时。

### 3.2 Diff 服务压力测试
- **场景 A：常规比对**：简单 JSON，全量对比。
- **场景 B：复杂规则比对**：包含 SORT 排序、数十条 SCRIPT 脚本规则、大型嵌套 JSON。
- **指标**：最大 TPS、平均耗时、规则匹配效率。

### 3.3 数据库与存储稳定性
- 针对 `migration_diff_record` 表进行千万级至亿级数据的写入与查询测试。
- **指标**：MySQL CPU/IO 负载、Admin 列表/详情/统计查询耗时。

## 4. 测试实施细节 (How to Test)

### 4.1 执行路径
1. **建立基准 (Baseline)**：原生调用（无注解），运行 10 分钟，记录 RT 和 TPS。
2. **阶梯压测**：通过 Nacos 动态切换状态，依次记录 7 个阶段的指标。
3. **损耗量化**：计算各阶段相对于基准的损耗比例。

### 4.2 工具链
- **流量产生**：Apache JMeter 或 Locust。
- **监控观测**：Prometheus + Grafana (JVM, CPU, Memory, TPS, RT)。
- **深度分析**：**Arthas** (使用 `profiler` 生成火焰图，定位 `MigrationInterceptor` 耗时)。
- **队列监控**：监控 SDK Disruptor RingBuffer 的剩余容量。

### 4.3 环境要求
- **SDK Mock 服务**：4C 8G。
- **Diff 服务**：8C 16G。
- **MySQL**：16C 32G (SSD)。
- **压测机**：16C 32G。

## 5. 核心关注点与瓶颈分析
- **JSON 解析**：Jackson 与 zjsonpatch 在 Diff 服务中的计算压。
- **线程上下文切换**：SDK 与业务共用线程池或异步交互时的开销。
- **DB 慢查询**：大量写入后的索引压力及统计查询性能。
- **队列背压**：Disruptor 满后的处理策略（CallerRuns 等）。

## 6. 执行步骤
1. 环境准备与数据预制。
2. 业务基准测试。
3. 7 阶段循环压测。
4. 性能分析与调优（如发现响应时间异常，使用 Arthas 诊断）。
5. 输出最终性能评估报告。
